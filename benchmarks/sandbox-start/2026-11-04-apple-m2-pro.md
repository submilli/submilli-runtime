Across both runs, p50 is reasonably stable at about 3.5 ms warm and 7.5–7.9 ms

## Method

Sandbox start uses `std::time::Instant` in `measure_start`. **t0** is immediately
before marker-state allocation and per-run VFS creation. **t1** is the timestamp
on entry to the marker host import, called by the first Wasm instruction of the
start function: `call marker; end`. The module has one import and one 64-KiB
linear memory, with no earlier guest instructions, global initializers, data
segments, or Package initializers. The timestamp precedes marker counters and
result serialization.

The interval includes:

- Ephemeral scratch-directory creation and Capability handle/metadata work with
  `Vfs::tempdir`, or `Vfs::none()` for the `none` mode.
- Run-ID generation, fresh `StoreData`, a fresh `PolicyCheck` for an already
  parsed Blueprint, and variables.
- Store, fuel, stack-limit and tenant-memory-limit setup; full runtime and
  marker import installation; and per-store GC/prelude state.
- Instance creation, initial linear memory, interpreter execution-stack
  allocation, and dispatch into the first marker call.

It excludes process boot, worker-thread/native-stack and async-executor
construction, engine creation, Blueprint parsing, `Module::new` validation and
lowering, TypeScript parsing/type-checking/code generation, remaining guest
execution, and store/linker/VFS teardown. Cleanup finishes between starts but is
not timed. The reusable native worker-thread stack is 16 MiB. The Wasm stack
budget is 512 KiB and the tenant memory cap is 50 MiB; caps do not mean that all
those bytes are allocated or touched. Fuel is 1,000,000,000,000 with an async
yield interval of 10,000 fuel.

The harness calls the production runtime functions, including
`StoreData::with_vfs_and_cap`, `RuntimeConfig::store_async`,
`install_tenant_limits`, `install_runtime_async`, and
`instantiate_program_async`. It uses full CLI-style linker setup. The HTTP
server reuses a base host-function linker, so this is not its exact request
path. No HTTP, Package loading, session persistence, credentials, or network
calls are exercised. Marker allocation/registration, first-call dispatch, and
clock-read overhead remain in the sample; nothing is subtracted.

**Warm:** each repetition and VFS mode uses one process, 1,000 warmups, and
10,000 measured starts. The engine and prepared marker module are reused;
per-run state is fresh. **Cold:** each repetition and VFS mode uses 200 fresh
processes, one sandbox per process, and zero warmups. Engine, module, Blueprint,
and process infrastructure are prepared before timing, with no earlier runtime
installation or instantiation. At this base, the prelude is Rust host functions;
there is no hidden prelude Wasm sandbox.

Each mode has three repetitions. Quantiles use nearest rank:
`ceil(percentile / 100 × count)`, one-indexed in sorted samples. Each median row
is the median of each statistic across the three repetitions, not a pooled
quantile. Its max column is the median of repetition maxima, not the worst
observed maximum. No outliers are removed. Modes run in fixed order: warm
`ephemeral`, warm `none`, cold `ephemeral`, cold `none`.

Cold resets process-local state, but not OS file/page caches, CPU caches, shared
libraries, or filesystem state. Warm also retains engine type tables, lazy
runtime state, and allocator caches. The engine is the `submilli-wasm` 0.1.12
interpreter, aliased as `wasmtime`; this is not a JIT/AOT cache comparison.
`Instant` stores integer nanoseconds, which does not establish accuracy. The
post-sample minimum nonzero back-to-back clock-read probe was 41 ns in each
group in both runs; it is not a calibrated accuracy test.

### Process boot and CLI first-run

Process boot is measured separately, from parent `Popen` begin to reader
observation of the worker's first flushed READY line, the first action in Rust
`main`. It includes spawning, dynamic loading, stdout IPC, and parent scheduling.
It is a proxy, not exact exec-to-main time. Engine/module/thread preparation
occurs after READY and before sandbox timing, so adding boot and sandbox start
does not give total request time. Warm boot rows have only one launch per
repetition; cold boot rows have 200.

CLI first-run is one set of 50 fresh invocations of
`function main(): number { return 0; }` with `run --report`, default ephemeral
VFS, telemetry disabled, and an isolated shared temporary `SUBMILLI_HOME`.
Every result is checked to equal `0`. There are no three-repetition CLI medians.

The CLI **compile bucket is not pure compile time**. It begins at
`execute_on_this_thread` before reading source and includes parsing,
type-checking, code generation, and CLI setup: engine, VFS, store, limits, module
preparation, and linker creation. It ends before runtime import installation.
The run bucket covers imports, instantiation, main, result conversion, and
blocking-work drain. Report wall is their sum before millisecond truncation;
it excludes process boot and final store/VFS teardown. Parent process-total
includes launch, output handling, and exit/teardown. No pure compiler-time
figure is inferred from these buckets.

## Important caveat on “start”

In real programs, a script's top-level statements compile into the Wasm start
function and execute during instantiation in `instantiate_program_async`.
In this harness, the marker is the first instruction of that function, so no
script top-level code is timed.

A measurement ending when instantiation returns, or a “start” bucket in
`--report` that covers instantiation, would include top-level code executed
during instantiation. The measured CLI report here calls its broader bucket
`run`. These sandbox-start results apply only to the trivial marker program;
compiler-generated and Package-heavy programs can do additional work.

## Load averages and load caveats

| Run | Interval on 2026-11-04 (UTC) | Start load, 1 / 5 / 15 min | End load, 1 / 5 / 15 min |
| --- | --- | --- | --- |
| 1, earlier | 11:04:25–11:08:56 | 4.11 / 8.97 / 23.37 | 2.10 / 5.05 / 17.68 |
| 2, low-load rerun | 12:02:10–12:06:53 | 1.55 / 1.45 / 1.88 | 1.88 / 2.13 / 2.11 |

Run 1 followed Remotion video renders that had overloaded the Mac, with load
averages near 100. Its high 5- and 15-minute averages retained that history.
Run 2 ran concurrently with a Codex CLI session and an `uptime` logger sampling
every 30 seconds. The logger timestamps are IST (UTC+2); the nine samples inside
run 2 span 14:02:24–14:06:25 IST. Their load ranges were 1.80–3.93 (1 minute),
1.51–2.36 (5 minutes), and 1.90–2.18 (15 minutes). Endpoint load alone does not
describe the whole run, and load averages do not establish the cause of an
individual latency spike.

Neither run used CPU pinning, frequency control, or an isolated host. Thermal
stabilization and other system activity were not controlled. An earlier release
build was paused at 303 MiB free disk space and resumed after space recovered;
all session builds/tests finished before run 1. Run 2 used `/tmp` for temporary
files; run 1 used `/var/folders/sn/km96m3_s4r91r4qdyk10h1rc0000gn/T`.
Ephemeral VFS measurements include real filesystem work, so the temporary-root
change is another comparison caveat.

The laptop's p99 and max values are not trustworthy as stable tail-latency
estimates. p50 is reasonably consistent across the two runs. Lower load did not
uniformly reduce latency: warm and cold/ephemeral tails increased, while
cold/none tails decreased. Fixed ordering, scheduling, caches, and sample size
limit interpretation. With 200 cold samples, p99 is the 198th ordered sample;
with 50 CLI samples, p99 equals max. The first run's 577.170 ms warm/ephemeral
boot outlier is retained in its raw data and lies outside sandbox timing.
