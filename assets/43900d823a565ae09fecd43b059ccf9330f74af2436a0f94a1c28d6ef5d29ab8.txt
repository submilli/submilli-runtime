1. Start with the program
An agent needs to total a customer’s charges. It writes a short program: fetch the charges, add them up, return the total. Submilli gives that program a place to run. The language, compiler, and runtime are designed together around code an agent writes and may need to repair. Let’s follow that program and see what those choices buy us.

Start with the language. TypeScript gives the agent familiar functions, loops, objects, and type annotations. Submilli implements its own version so it can change the rules where that helps generated code. There is no any type to bypass checking. Raw JSON arrives as unknown. When the program casts it to a specific type, Submilli checks the value’s shape at runtime. If an amount arrives as text instead of a number, the cast fails there. The agent gets a failure at the bad assumption, before that value travels through the calculation. Familiar syntax helps it write the program; stricter checks help it repair one.

2. Why Submilli packages
The program uses Submilli’s standard library and installed packages. Why not accept any N P M dependency? Those libraries may expect Node’s filesystem, process model, or other facilities that this runtime does not provide. Supporting them would mean carrying those expectations into the execution environment. With Submilli packages, you choose the available integrations before the run. Package authors put permission checks around the actions they expose. An ordinary N P M library does not supply those checks. A billing package exposes a typed operation such as listing charges. Dependencies are pinned and recorded in a lockfile. The agent can compose the operations you provided without assembling a new software environment for each task. That trades unrestricted library choice for an interface the application can prepare and control.

The compiler also helps the agent fix its work. Here, the program misspells amount. The diagnostic marks the field, suggests the correct spelling, and includes the type declaration. The agent has a concrete correction to make. Once the program passes these checks, Submilli compiles it to WebAssembly. Package modules are built ahead of the run and linked alongside it. Both execute through the same runtime. This gives Submilli a defined instruction format to execute and meter, while the agent continues to write readable TypeScript.

3. Run inside the Submilli server
Your application sends the program to the Submilli server over H T T P or M C P. Inside that existing process, the runtime creates an execution instance and runs the compiled code with Submilli’s WebAssembly interpreter. Each instance holds the program’s state and has resource limits. The program can call supported host operations, which handle work such as service requests. This arrangement puts execution and its controls together, without starting a separate operating system for each program.

4. What each run needs
That matters when you run many agents. A micro V M provides a hardware virtualization boundary, with a guest operating system and memory to provision. Submilli creates WebAssembly instances inside the process it already has. Compilation and instance setup still take work, but there is no guest operating system to boot for each run. When one program waits for a service, the runtime can yield while other runs make progress. It is a different isolation boundary from a micro V M, so the runtime and its host operations remain part of what you trust.

Useful failures are another part of the design. Submilli’s GitHub package can report that a branch has moved since the agent read it. The agent can read the current branch and reconsider its edit. A rate limit error can carry retry timing when the service provides it. The caller can decide when to try again; the package does not retry automatically. These errors distinguish a stale assumption from a temporary limit. That gives the agent a specific next step instead of repeating the same failed call. Purpose-built packages can make the operation, its permission checks, and its recovery information one documented interface.

5. Check the operation before the effect
Now return to our billing example. We build the package so that listing charges first checks the requested operation and customer. The runtime evaluates that check against the blueprint you created and the context your application supplied. A rule can require the requested customer to match Customer A. A request for Customer A can proceed. The same function called for Customer B can be denied before the lookup. The check sits inside the package, so it is part of performing the operation. The generated program does not get to decide whether its own request is allowed.

6. An environment for generated code
These choices work together. Familiar TypeScript gives the agent a practical way to express the task. Stricter checks and specific errors help it find and repair mistakes. WebAssembly lets the runtime execute and meter the program inside an existing process. Packages provide the operations, and blueprints define their permitted use. The result is an environment built for generated code: the agent can compose useful work and respond to failures, while your application defines the access and resources it receives.
